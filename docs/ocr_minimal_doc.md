# Unified OCR API Specification (Minimal)

## POST `/v3/ocr`
- Purpose: queue one or more files for OCR processing.
- Request: `multipart/form-data`
  - `files`: one or more file parts; supported extensions `.jpeg`, `.png`, `.pdf`, `.jpg`, `.tif`, `.tiff`.
  - `metadata` (optional): JSON string representing an array ordered to match the uploaded files. Each item may include `guid` (string) and `format` (extension with leading dot). When omitted, the service assigns GUIDs and infers format from the filename.
  - `webhook_url` (optional): HTTPS URL to receive the final OCR payload. If blank or missing, clients must poll for results.
- Response `200`: JSON array of queue entries. Each entry contains:
  - `task_id`: workflow identifier (may be `null` if a file is rejected before queuing).
  - `status`: `"queued"` when accepted, `"error"` when the file is rejected (e.g., bad extension).
  - `guid`: identifier echoing metadata or auto-generated by the service.
- Example response:
```json
[
  {"task_id": "bd0d52f9-2a1d-4e2b-8bcb-0f3a6b8628d6", "status": "queued", "guid": "invoice-001"},
  {"task_id": null, "status": "error", "guid": "bad-file"}
]
```
- Notes:
  - Requests receive an `X-Correlation-ID` header; include it when contacting support.
  - Large uploads are staged server-side before dispatching to workers; keep the returned `task_id` per file for polling.

## GET `/v3/ocr/tasks/{task_id}`
- Purpose: retrieve the latest state for a queued OCR workflow.
- Path parameter: `task_id` from the queue response.
- Response `200`: JSON object with:
  - `task_id`: echoes the requested ID.
  - `status`: Celery task state (`PENDING`, `STARTED`, `RETRY`, `SUCCESS`, `FAILURE`).
  - `result`:
    - On success, `FinalOCRResult` with fields:
      - `guid`: GUID for the source file.
      - `text`: Base64-encoded UTF-8 OCR text.
      - `confidence`: average confidence (float).
      - `status`: `"completed"`.
      - `error`: empty string.
    - On failure, `TaskErrorResult` with `error` describing the failure.
- Success example:
```json
{
  "task_id": "bd0d52f9-2a1d-4e2b-8bcb-0f3a6b8628d6",
  "status": "SUCCESS",
  "result": {
    "guid": "invoice-001",
    "text": "8J+agA0K8J+agA==",
    "confidence": 0.92,
    "status": "completed",
    "error": ""
  }
}
```
- Failure example:
```json
{
  "task_id": "bd0d52f9-2a1d-4e2b-8bcb-0f3a6b8628d6",
  "status": "FAILURE",
  "result": {
    "error": "Unsupported file format: .txt"
  }
}
```
- Clients must Base64-decode the `text` field (`utf-8`) before use.

## Webhook Callback (Optional)
- Triggered only when `webhook_url` is provided to the queue endpoint.
- Method: `POST` to the client-supplied URL with `Content-Type: application/json`.
- Payload mirrors the polling response:
  - On success: `task_id`, `guid`, `text` (Base64), `confidence`, `status: "completed"`, `error: ""`.
  - On failure: `task_id`, `guid`, `text` (always Base64, empty string on failure), `confidence: 0.0`, `status: "error"`, `error` populated with the failure reason.
  - The service always includes a non-null `task_id`; when the original ID is unavailable a fallback UUID is supplied and logged.
- Delivery guarantees:
  - The service attempts up to 3 deliveries (initial call plus 2 retries) with ~10 s between retries when network errors, timeouts, or non-2xx responses occur.
- Security: HTTPS is required unless administrators enable insecure webhooks; supply verifiable endpoints and handle the `X-Correlation-ID` header if present.

## Health Check
- `GET /` returns `{"message": "OCR Service is running"}` when requested with `Accept: application/json`. Browsers receive the HTML UI instead.
